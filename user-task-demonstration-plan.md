Add user task demonstration recording to web-ui, distinct from the existing agent action recording. This system will allow users to demonstrate tasks in their browser, save them as templates, and convert them into instructions that web-ui agents can follow.

## 2. Screen Recording Options for Browser Interactions

**Playwright’s Built-in Video Capture:** Playwright supports recording a video of the browser session natively. We can enable this by setting the `record_video_dir` option when launching a browser context, causing it to save an MP4/WebM of all actions in that context ([Videos | Playwright Python](https://playwright.dev/python/docs/videos#:~:text=With%20Playwright%20you%20can%20record,videos%20for%20your%20tests))  This is useful for **screen recording**, allowing us to store a visual log of what happened (for the user to review or for debugging). The video is saved when the context closes ([Videos | Playwright Python](https://playwright.dev/python/docs/videos#:~:text=Videos%20are%20saved%20upon%20browser,sure%20to%20await%20%2048))  For example, we could start video capture when the user hits “Start Recording” and finalize the video when they stop. This yields a file showing exactly what the user did on screen. However, this video alone isn’t directly useful for the LLM (since the model can’t watch a video), but it’s a helpful reference for humans. It can be stored alongside the workflow as documentation or for replay verification.

**Playwright Codegen (Interaction Script Recording):** Apart from video, **Playwright’s codegen tool** can record interactions and generate script code for them ([Test-Automation Playwright Tool Now Records and Replays Interaction Scripts, Captures Test Videos - InfoQ](https://www.infoq.com/news/2020/10/playwright-records-scripts-tests/#:~:text=Newly%20released%20Playwright%201,record%20videos%20of%20test%20scripts))  In CLI form, this opens a browser for the user and captures clicks and typing, producing a Playwright script that reproduces those actions. We can attempt to harness a similar capability programmatically. One approach is to run Playwright’s recording in the background: e.g., use the DevTools protocol to listen to DOM events or use `page.on('framenavigated')`, `page.on('click')`, etc., to log actions. If Playwright’s Python API doesn’t expose a high-level recorder, we might emulate it: for each user event, identify the target element and produce a selector (Playwright’s built-in heuristics for selectors could be leveraged by calling `page.locator(...).selector()` or using the same logic as codegen to get robust selectors ([Test-Automation Playwright Tool Now Records and Replays Interaction Scripts, Captures Test Videos - InfoQ](https://www.infoq.com/news/2020/10/playwright-records-scripts-tests/#:~:text=npx%20playwright)) . The goal is to capture a **structured log** of actions (which we detail in the next section). 

**Alternative Capture Approaches:** If direct event hooks prove difficult, another approach is injecting a snippet of JavaScript into pages while recording. For example, we could attach `document.addEventListener('click', ...)` to log clicked element identifiers, or override `HTMLElement.prototype.click` in the page context to notify our Python code. Similarly, for text input, monitor `input` events. This approach would yield event details that we can then translate into high-level steps (like “click selector X”). We should also capture page navigations (via Playwright’s `page.on('navigate')`) and form submissions. This ensures no user action goes unnoticed even if it doesn’t trigger a DOM event (e.g., selecting an option or scrolling).

**Storing the Recording:** Along with the structured log, we may also capture **periodic screenshots or a GIF** as a lightweight “screen recording.” For instance, after each recorded step, take a screenshot. This gives a step-by-step visual that an LLM could theoretically analyze or that a user can see during replay. However, storing many screenshots can be heavy; a video (as above) might actually be more storage-efficient for long sessions. We’ll weigh these trade-offs. For the MVP, the simplest route is: *enable Playwright’s video recording for visual feedback*, and *focus on capturing structured events for automation*. 

In summary, **Option A**: use Playwright’s built-in video to record the screen for user reference ([Test-Automation Playwright Tool Now Records and Replays Interaction Scripts, Captures Test Videos - InfoQ](https://www.infoq.com/news/2020/10/playwright-records-scripts-tests/#:~:text=Newly%20released%20Playwright%201,record%20videos%20of%20test%20scripts))  **Option B**: capture structured events using Playwright’s codegen capabilities or custom event listeners, yielding a script or JSON that the LLM can later follow. Both can be done in parallel: record a video for auditing and collect events for the automation logic.

## 3. Workflow Recording Mechanism and Data Format

**Capturing Interactions as Structured Data:** When recording, each browser interaction should be logged in a structured format that an LLM agent (or any automation script) can interpret and replay. We will define a **workflow schema** that includes key details of each step: the action type, a selector or identifier for the target element, any input data, and perhaps expected outcomes. For example, a recorded workflow might be represented as an array of steps in JSON or YAML, e.g.: 

```json
[
  {"action": "navigate", "url": "https://example.com/login"},
  {"action": "fill", "selector": "input#username", "value": "alice"},
  {"action": "fill", "selector": "input#password", "value": "••••••"},
  {"action": "click", "selector": "button[type=submit]", "description": "Login"}
]
```

Each entry describes what the human did. We’ll favor **high-level descriptors** (like “click button ‘Submit’”) over raw coordinates. Playwright can help determine good selectors for each element as it does in its test generator, which **prioritizes roles, text, and test IDs to create resilient selectors**, refining them to uniquely identify the element ([Test-Automation Playwright Tool Now Records and Replays Interaction Scripts, Captures Test Videos - InfoQ](https://www.infoq.com/news/2020/10/playwright-records-scripts-tests/#:~:text=npx%20playwright))  By using these robust selectors, we ensure the recorded steps remain valid even if the page structure changes slightly (e.g., different classes or positions) ([Test-Automation Playwright Tool Now Records and Replays Interaction Scripts, Captures Test Videos - InfoQ](https://www.infoq.com/news/2020/10/playwright-records-scripts-tests/#:~:text=npx%20playwright))  

**Elements of the Workflow Structure:** At minimum, we store: 
- **Action type** – e.g., “navigate”, “click”, “fill (type text)”, “select (dropdown)”, “scroll”, etc. This tells the agent what operation to perform.  
- **Target selector or locator** – a way to find the element in the DOM. We’ll use CSS/XPath selectors or Playwright’s locator syntax (which can include text, aria roles, etc.). For navigation, the target might be a URL instead. For scrolling, it might be an element or coordinates.  
- **Input data** – if the action is typing or selecting a value, record the text or option. (Passwords or sensitive fields might be masked or referenced by a placeholder as discussed in security.)  
- **Metadata (optional)** – this could include a human-readable description (e.g., “Click the Login button”), or an assertion about the state (“expect navigation to dashboard page after clicking”). While not strictly necessary to replay, these can provide context to an LLM if it needs to reason about a step.

**Ensuring Interpretability by LLM:** The format should be easy for an LLM agent to consume. One approach for the MVP is to bypass complex natural language parsing by having a straightforward JSON that a programmatic agent can execute. However, if we want the LLM itself to interpret and execute steps, we could feed it the structured steps as part of a prompt (e.g., “Execute the following steps one by one: 1. Go to URL..., 2. Click ‘Submit’ button, ...”). Since OpenAI models now support function calling, another idea is to define a function schema for each action type (like a function `click(selector)` that the model can call). The model could then read the steps and call the corresponding function for each, making the process interactive and auditable via the model’s decisions. In practice, though, having the **steps already determined by the human recording means the LLM doesn’t need to plan**, it only needs to carry them out. This reduces the cognitive load on the model and number of API calls.

**Resilience and Repeatability:** To make replays repeatable, the recorded workflow might need to include some timing or waiting info. Playwright implicitly handles waits with its auto-wait feature (so our agent should naturally wait for an element to be ready before clicking) ([Auto-waiting | Playwright](https://playwright.dev/docs/actionability#:~:text=Playwright%20performs%20a%20range%20of,TimeoutError))  We could also insert explicit waits in the log if needed (e.g., “wait for selector X to appear”). The stored workflow could allow future editing – for instance, the user might generalize a hard-coded value into a parameter. Designing the structure as a serializable object (JSON/YAML) will make it easier to later save, edit, or even share workflows. For the MVP, we focus on capturing exact interactions as they happened, in sequence.

**Example Workflow:** As a quick illustration, if a user’s recorded task is “Search for a product and add to cart”, the stored workflow might look like:
1. **navigate** – URL: `https://shop.com`  
2. **fill** – selector: `input[name="q"]`, value: `"laptop"`  
3. **click** – selector: `button#search` (text “Search”)  
4. **click** – selector: `a.product-link` (text contains “Laptop XYZ”)  
5. **click** – selector: `button.add-to-cart` (text “Add to Cart”)  

This sequence can be saved as a JSON file under a name like “Search and Add to Cart.json”. It is human-readable and LLM-readable. The LLM agent, when replaying, could be given this structured plan and it simply executes each step in order, making the same browser manipulations the human did.

## 4. Execution Pipeline for Recorded Workflows

**Initiating a Replay:** Users will be able to select a recorded task from a list in the UI and trigger the **execution**. When execution starts, the system launches or reuses a browser session (depending on whether we want a fresh session or a continued one – more on that shortly) and the LLM agent (or a direct script runner) begins performing the steps from the stored workflow. We’ll provide a **“Run Workflow”** button next to each saved task in the UI. On click, it might prompt the user whether to run in the current browser session (if one is open) or a new session (to isolate it).

**Real-time Observation:** As the LLM or script carries out the steps, the user should be able to observe what’s happening, just as they can when the AI agent normally operates. Currently, the WebUI uses a noVNC web viewer to let the user see the browser interactions in real time ([GitHub - browser-use/web-ui: Run AI Agent in your browser.](https://github.com/browser-use/web-ui#:~:text=,time))  We can integrate this viewing directly into the Task Recording tab during replay. For instance, an iframe or canvas in the tab could show the live feed of the browser so the user watches each click and navigation. If using the user’s own browser, they will literally see the pages loading and elements being clicked in their browser window. If using a headless or remote browser, the noVNC approach (or periodic screenshots) can serve as the visual feedback. The interface can also highlight the current step being executed (e.g., “Step 3 of 5: Clicking ‘Add to Cart’ button…”), perhaps by highlighting the corresponding line in the workflow list.

**User Intervention and Controls:** It’s crucial to allow human intervention if something goes wrong or if the user wants to adjust the process. We will include **controls like Pause, Resume, and Stop**. Pause will halt the execution after completing the current step, allowing the user to inspect the state or even manually perform a correction. The user could, for example, pause if a step is failing (say the “Add to Cart” button was not found because the item is out of stock) – they might manually navigate or choose a different item, then decide to either stop or resume (skipping the problematic step). Resume will continue the automated sequence from where it left off (or the next step). Stop will abort the run entirely. If stopped, we could offer to save the partial execution state or not.

**Ensuring Repeatability and Determinism:** To reliably replay tasks, especially in **client-side sessions**, we need to consider initial state. If the workflow assumes a fresh login or empty cart, running it in a browser that has leftover state might cause different outcomes. For MVP, we can document that users should start recordings from a known state (or always begin with a fresh incognito session when replaying). As an enhancement, the system could automatically open a new browser context for each replay to ensure isolation – or include a “Reset session” action as the first step of a workflow (for example, going to a homepage and logging out if needed). Using persistent sessions has the benefit of keeping authentication and history (so you don’t have to log in every time) ([

](https://www.deskriders.dev/posts/1737221182-linklist-2025-01-11/#:~:text=,installed%2C%20Git%20to%20clone%20repository))  which is user-friendly, but it can reduce repeatability if not managed. A flexible approach is to let the user decide: e.g., a checkbox “Reuse last session (keep cookies)” vs. “Start new session”. For now, we might default to reusing the session to leverage any logged-in state (since the WebUI specifically supports persistent sessions for continuing tasks ([
  Link List :: 2025-01-11 · deskriders
](https://www.deskriders.dev/posts/1737221182-linklist-2025-01-11/#:~:text=,installed%2C%20Git%20to%20clone%20repository)) , and require that the workflow itself handles any necessary resets.

**LLM Involvement During Execution:** Ideally, replaying a recorded workflow doesn’t require heavy reasoning from the LLM – it’s a deterministic script. We could implement the execution as a direct script (each step calling Playwright functions) without asking the LLM to generate anything. This would be efficient and avoid API calls. However, one **advantage of involving the LLM agent** is flexibility: if a step doesn’t exactly match (e.g., the selector no longer finds an element), an intelligent agent could try to interpret the intent (maybe using the step description or similar elements) to recover – whereas a hard script would just fail. For MVP, a safe approach is to run the steps as is, but if a step fails, catch the exception and then trigger an LLM reasoning cycle. For example, if a click fails due to element not found, we pause and ask the LLM (with the page context) “The recorded step was to click ‘Add to Cart’ but that element isn’t present – what should we do?” The LLM might then search the page for a similar button text or report an error. This mix ensures robustness without involving the LLM when it’s not needed. 

**User Prompting and Debugging:** During execution, we will surface any issues to the UI. If a step fails and no automatic recovery is done, we can show an error message at that step and allow the user to intervene (either manually perform that step, or edit the workflow and retry). We might also allow **step-by-step mode**, where the user can advance one step at a time with a “Next Step” button. This is useful for debugging a recorded workflow or for training purposes (the user can observe each action and ensure it’s correct).

**Completing the Execution:** Once all steps have executed, the UI should indicate success (maybe “Workflow completed successfully” along with the total time taken). The browser session can remain open (especially if persistent mode is on, letting the user inspect the final state or continue browsing). If it was a one-off session, we may close the browser or present an option to keep it open. The outcome of the workflow (like any result data) could be captured – e.g., if the task was “scrape these prices and send to me”, the LLM agent would return the data at the end. In general, the pipeline will mimic how a human did the task, with the user in the loop to watch and intervene, thereby fostering trust and reliability in the automation.

## 5. Storage and Security Considerations

**Local Storage for MVP:** For the minimum viable product, we will store recorded workflows **locally on the user’s machine** (or server where the WebUI is running). This could be in a predefined directory (like `workflows/`) or a lightweight database (like an SQLite file). Local storage is simple and avoids any network or cloud complications. Each saved workflow can be a file containing the JSON/YAML structured steps and any metadata (like the name, date, maybe a brief description the user gives). Storing locally keeps things under the user’s control – important since the interactions may include sensitive data (like what websites they visited, form data, etc.). We will ensure the file permissions are such that only the appropriate user/process can read them, especially if the system is running on a multi-user server.

**Sensitive Data Handling:** A major security consideration is that the recorded interactions might contain private information: login credentials, personal data entered into forms, etc. We must **avoid leaking secrets** in these stored files. For example, if a password field is typed during recording, the raw text of the password should not be saved in plain JSON. As a solution, we can detect inputs into password fields (Playwright can identify `<input type=password>` or we can mark any field the user wants to mask) and instead store a placeholder like `"<<PASSWORD>>"` or a reference to a secure secret. The system can then either prompt the user at replay time to enter the password, or fetch it from a secure location if one is configured. Similarly, other highly sensitive info (credit card numbers, etc.) could be handled in a special way – but password is the most obvious case. For MVP, we’ll likely implement just a simple rule: don’t record the actual value of password fields, and on replay, pause and ask the user to input it (or require them to have logged in already via persistent session).

**Preparing for Future Security Enhancements:** While local plain storage is OK for an MVP on a personal machine, we want the design to be flexible for enterprise or cloud scenarios. In the future, we might need to encrypt stored workflows or store them in a secure database with access control. We should abstract the storage layer enough so that switching from local files to, say, an encrypted SQLite or a cloud store is possible without changing the core logic. For example, have a `WorkflowStorage` class with methods like `save_workflow(name, data)`, `load_workflow(name)` so that later we can modify those methods to add encryption or authentication. One idea is to use the user’s OS keychain or a password the user provides to encrypt sensitive parts of a workflow (so even if the file is accessed, the critical info isn’t in plain text). 

Additionally, we should guard the recording mechanism such that it doesn’t accidentally expose data to the LLM when not intended. Since our aim is to keep everything local, by default the workflows won’t be sent anywhere. But if the user decides to share a workflow file with someone, we’ll note that they should scrub any private data first. In an upgraded version, a cloud service could allow sharing workflows between users with proper OAuth and encryption, but that’s beyond MVP scope.

**Security of Execution:** Another concern is authentication during execution. We prefer to use the existing session cookies via custom browser support to avoid storing login credentials at all ([
  Link List :: 2025-01-11 · deskriders
](https://www.deskriders.dev/posts/1737221182-linklist-2025-01-11/#:~:text=,installed%2C%20Git%20to%20clone%20repository))  For example, if the user is already logged in on their own browser, the recorded workflow might not include any login step – it just assumes the session is live. That’s great for security (no credentials in workflow), but it means the workflow is tied to the user’s environment. For now, that’s acceptable. We will document that workflows may not be portable if they rely on an authenticated session (unless the login step is recorded and the credentials handled securely). 

**Limiting Scope in MVP:** To keep development focused, we will implement basic protections (mask passwords, store files locally) and defer heavier security (encryption, vault integration) to future iterations. We will *not* let security needs block the core functionality: for instance, if handling login securely is tricky, we might simply require the user to be logged in already or prompt them manually, rather than engineering a full secret storage system immediately. We will also avoid sending any recorded data to external services (including not feeding entire recorded sequences to the OpenAI API unless necessary for the LLM to understand – and even then, we can abstract or anonymize as needed). By isolating data locally and giving the user control, we mitigate a lot of risk at the MVP stage. 

In summary, **store workflows locally** in a structured format, **mask or omit sensitive info** in those records, and use **existing browser sessions for auth** where possible to avoid storing credentials. This approach keeps the design simple and confines potential security issues to the user’s environment, which we can progressively harden (e.g., encrypting files or integrating with secure credential stores) as the project evolves.

## 6. Key Implementation Challenges & Proposed Solutions

### Deterministic UI Interactions
**Challenge:** Replaying interactions must be deterministic – the workflow should behave the same way each run, without flakiness. In web automation, dynamic content loading or timing issues can cause flaky behavior (e.g., clicking before an element is ready, or elements shifting). Also, if multiple similar elements exist, the recorded selector might match the wrong one later unless it’s robust.

**Solutions:** We will leverage Playwright’s **auto-wait and actionability checks** to ensure each step executes under the right conditions. Playwright automatically waits for elements to be visible, enabled, and stable before interacting ([Auto-waiting | Playwright](https://playwright.dev/docs/actionability#:~:text=Playwright%20performs%20a%20range%20of,TimeoutError))  This means our agent executing the steps will not, for example, click a button until it’s actually rendered and clickable, reducing race conditions. We’ll also make sure to use **unique and resilient selectors** for elements. Instead of relying on brittle XPaths or indexes that might change, we use text or role-based selectors that are more stable ([Test-Automation Playwright Tool Now Records and Replays Interaction Scripts, Captures Test Videos - InfoQ](https://www.infoq.com/news/2020/10/playwright-records-scripts-tests/#:~:text=npx%20playwright))  For instance, selecting a button by its label text “Add to Cart” is more robust than using a CSS path that could shift with layout changes. Playwright’s recording functionality attempts to refine selectors to uniquely identify targets and tolerate minor DOM changes ([Test-Automation Playwright Tool Now Records and Replays Interaction Scripts, Captures Test Videos - InfoQ](https://www.infoq.com/news/2020/10/playwright-records-scripts-tests/#:~:text=npx%20playwright))  which we will utilize.

To further ensure determinism, the recorded workflow might include **assertions or checkpoints**. For example, after a navigation step, we could implicitly assert that the new page’s title or a specific element is present (matching what the human saw). This way, if a navigation unexpectedly redirects or a popup appears, the agent can detect the deviation. These checkpoints act as guardrails so that the script doesn’t blindly continue in an unexpected context. If any check fails, the execution can pause and alert the user.

Another tactic is controlling randomness: if the task involves any random outputs (perhaps not likely in a deterministic workflow), we’d capture those outputs or seeds. However, most human-recorded tasks won’t involve deliberate randomness, so this is minor.

In summary, using Playwright’s robust waiting and reliable element targeting will address most nondeterminism. The approach mimics best practices in test automation: *wait for the UI state you expect, then act*. By design, a recorded workflow is linear and does the same things each time, so as long as the web page itself hasn’t changed in a breaking way, the automation should perform consistently. We plan to test each recorded workflow multiple times to ensure repeatability, adjusting selectors or adding waits if any flakiness appears.

### Preserving Business Logic and Context in Replays
**Challenge:** Human actions often involve implicit decision-making based on context (business logic). For example, “if the price is above $100, apply a discount code, otherwise skip that step” – a human might do this intuitively, but a recorded linear workflow would either always apply the code or not, lacking the conditional. Similarly, if the interface or data changes (like an item name updated), a naive replay might fail to find “Laptop XYZ”. We need to preserve or allow the **reasoning** that a human applied, to make the automation robust to context changes.

**Solutions:** For the MVP, we will assume that the recorded workflow is mostly for the same context it was recorded in (so minimal changes). However, we will design the system with the possibility of **parameterization and conditional logic** in mind. One immediate step is to allow certain inputs to be marked as **variables**. For instance, the user could label the product name or price threshold as a variable in the workflow script. Then at replay time, they can input a new value or have the LLM decide it. While implementing a full scripting language with conditionals is complex, we can start by structuring the recorded data in a way that’s extensible (e.g., it could include an optional condition field or allow the insertion of an “if” block in a future version).

More directly, we can use the LLM’s intelligence during replay to handle slight deviations. The recorded steps come with context like element text. If a step fails (element not found) or if we explicitly ask the LLM to verify something (“Is the price > $100?”) as part of the workflow, the LLM can make a decision. For example, we might insert a pseudo-step in the workflow: `{"action": "if", "condition": "price > 100"}` followed by steps to apply a coupon. The agent could evaluate that condition at runtime by checking the page (with LLM help if needed to parse the price text). For MVP, we won’t have a UI for users to define such logic, but we can **preserve context** by capturing extra attributes of elements. 

Specifically, when recording a click on an element, besides storing the selector, we could store identifying text of that element or nearby labels. This is akin to how next-gen testing tools capture *dozens of attributes for every element* to improve resiliency ([4 Ways to Make Record and Playback Test Automation Not Suck | mabl](https://www.mabl.com/blog/make-record-and-playback-test-automation-not-suck#:~:text=1,UI%20locators))  For instance, if the human clicked a button by icon (no text), we can note its `aria-label` or parent text. Later, if the UI changes the button’s ID, the agent could still find it via the label. This is a passive way to encode context into the workflow.

For more complex logic preservation, we envision a **“generalize with AI”** feature: the LLM could take a recorded workflow and produce a more abstract or condition-aware version. E.g., it might comment that “Step 5 is only needed if condition X holds” based on the page content at recording time. That’s aspirational; initially, we focus on straight-line tasks.

Another measure: instruct the LLM agent (if it’s overseeing execution) to not strictly follow the script if the outcome of a step clearly deviates from expectation. For example, after clicking “Place Order”, if the next expected step was “Verify confirmation message”, but instead an error message appeared, the LLM could catch that and maybe notify the user or try an alternative (this bleeds into error handling rather than pure recording, but it’s related to preserving the *intent* of the task – completing the order – even if execution needs adjustment).

**Bottom line:** While the MVP recorded workflow will be mostly static, we will capture as much relevant context as possible for each step (text content, element roles, etc.) so that replays are not brittle. We acknowledge that pure record-replay has limitations if the website changes ([4 Ways to Make Record and Playback Test Automation Not Suck | mabl](https://www.mabl.com/blog/make-record-and-playback-test-automation-not-suck#:~:text=maintenance,convoluted%20from%20automatically%20generated%20code))  so our long-term solution is to incorporate the LLM’s reasoning to adapt workflows. In the short term, we’ll advise users to re-record or adjust workflows if the target site changes significantly, and possibly provide an editing interface to tweak selectors or add simple conditions. This way, business logic can be updated by the user or an AI assistant, keeping the automation aligned with the intended decisions.

### Handling Authentication Securely (but Easily)

**Challenge:** Many automated tasks require logging into websites. Storing user credentials in the workflow is a security risk and asking the user to log in manually each time undermines automation. We need a way to handle authentication steps in recorded workflows securely, without significantly complicating the MVP implementation.

**Solutions:** The simplest approach leverages the **existing custom browser support** ([
  Link List :: 2025-01-11 · deskriders
](https://www.deskriders.dev/posts/1737221182-linklist-2025-01-11/#:~:text=,installed%2C%20Git%20to%20clone%20repository)) in the WebUI: users can connect their own browser profile to the tool, which means any login sessions they have are already in place. If the user is logged into a site in their regular Chrome and our Playwright attaches to that, then recorded actions on protected pages won’t need an explicit login step at all. This *eliminates the need to re-enter credentials in the workflow* ([
  Link List :: 2025-01-11 · deskriders
](https://www.deskriders.dev/posts/1737221182-linklist-2025-01-11/#:~:text=,installed%2C%20Git%20to%20clone%20repository))  sidestepping the issue. We will encourage this method for MVP: e.g., a user could log in to Gmail in their browser, then use the Task Recorder to record some email-sending steps – the recording will assume the user is authenticated and will not contain any password.

If a login must be recorded (say the user wants to automate the login itself), we’ll implement **credential masking and prompting**. During recording, if we detect the user typing into a password field, we capture an action like `{"action": "fill", "selector": "#password", "value": "__SECRET__"}` instead of the real password. That `__SECRET__` can map to a secure location (for MVP, maybe just a placeholder). On replay, when the agent hits this step, we pause and ask the user to input the password (or require that they have set an environment variable or config file with the password). This is not fully seamless, but it ensures we never store the password in plain text. For usernames or less sensitive fields, storing might be okay, but we could similarly allow users to mark any field as private.

In terms of storage, we keep all workflow files local (as mentioned), so exposure is limited. But if the user’s machine is compromised, those files could be read, so better not to have cleartext secrets at all. In future, integration with secure storage (like retrieving credentials from a vault or OS keychain) can be added. For now, an **environment variable approach** could be a compromise: e.g., record `<<ENV:MY_PASS>>` and instruct the agent to pull `MY_PASS` from the environment at runtime. The user would then ensure their password is stored as an env var before running. This is a common practice in test automation to avoid hard-coding secrets.

We will also warn users in documentation about the sensitivity of recorded data. For example, “Don’t share your workflow files if they contain personal data, unless you’ve removed or masked those parts.” Transparency is key: perhaps provide a view of the recorded script after recording, so the user can scrub any inadvertent sensitive info before saving. 

Another aspect is **session management**: Sometimes it’s preferable to not even log out. Because the WebUI can keep a browser session persistent, a recorded workflow might rely on a session cookie that remains valid ([
  Link List :: 2025-01-11 · deskriders
](https://www.deskriders.dev/posts/1737221182-linklist-2025-01-11/#:~:text=,installed%2C%20Git%20to%20clone%20repository))  We need to ensure that if a workflow is replayed much later, the session hasn’t expired – otherwise the workflow might break at a protected page. As a fallback, if during replay we detect a redirect to a login page (meaning the session expired or was missing), we could pause and notify the user (“Login required to continue this workflow.”). The user can then log in manually (since they’re watching the browser in real time), and once logged in, resume the workflow from the next step. This human-in-the-loop approach means we don’t have to automate storing the password, yet the workflow isn’t completely halted – the user just intervenes at that point.

For MVP, our plan is: **avoid storing credentials** if at all possible, lean on existing authenticated sessions, and when needed, interactively ask for credentials. This way we achieve automation in most cases without delaying the project for a full auth solution. We keep the architecture open to later plugging in a more sophisticated method (for example, some users might want to supply an API token instead of logging in via UI – we could allow the workflow to call an API or use an API key if the site supports it, as an advanced option).

In summary, we’ll handle authentication by **using existing login state** whenever possible to skip recording credentials ([
  Link List :: 2025-01-11 · deskriders
](https://www.deskriders.dev/posts/1737221182-linklist-2025-01-11/#:~:text=,installed%2C%20Git%20to%20clone%20repository))  If login must be part of the workflow, we’ll **mask sensitive inputs** and require user input at runtime (or use env variables) rather than store secrets. This strikes a balance between security and usability for the MVP.

### Avoiding API Limitations & Ensuring Smooth LLM Integration
**Challenge:** Integrating OpenAI (or other LLM) into this system introduces concerns about API rate limits, latency, and cost. Each step or decision could require an API call. OpenAI’s GPT-4, in particular, has strict rate limits (for example, around **200 requests/minute and 40k tokens/minute for the 8k model** as of mid-2023) ([GPT-4 rate limits are brutal; use GPT-3.5 instead | Sophia Willows](https://sophiabits.com/blog/gpt-4-rate-limits-are-brutal#:~:text=At%20the%20moment%20the%20limits,token%20limit%20of%20150%2C000%20tokens%2Fmin))  which can be *“punishing”* for interactive applications if not managed carefully ([GPT-4 rate limits are brutal; use GPT-3.5 instead | Sophia Willows](https://sophiabits.com/blog/gpt-4-rate-limits-are-brutal#:~:text=Something%20which%20doesn%E2%80%99t%20seem%20to,on%20in%20your%20product%E2%80%99s%20lifecycle))  We need to ensure the task automation feels responsive and doesn’t exhaust the allowed quota. Moreover, we want the LLM to reliably follow the recorded script without hallucinating or deviating – essentially using it in a deterministic tool-using mode.

**Solutions – Minimize API Calls:** A recorded workflow provides structure, so we do not need the LLM to *plan* every step from scratch. We can drastically **reduce the number of API calls** by not calling the LLM at all for straightforward step execution. For instance, if we have 20 steps recorded, a naive approach might be to prompt GPT-4 step by step (“Now do X”) 20 times. Instead, we can either (a) make one call to GPT asking it to execute the whole sequence (with function calls or a special role that executes steps), or (b) skip using GPT’s language understanding entirely and directly execute via Playwright. Option (b) is the most efficient – essentially treating the workflow like a script. This means for a replay we might not hit the API at all, unless an unexpected situation arises that requires “thinking”.

However, we do want to keep the **LLM in the loop for flexibility and monitoring**. A good compromise is to use OpenAI’s **function calling** feature for tool use. We can define functions like `navigate(url)`, `click(selector)`, etc., and give GPT-4 the workflow steps in a structured format, asking it to call these functions in order. GPT-4 with function calling can act in a *“more deterministic and structured manner”* ([Function Calling: Integrate Your GPT Chatbot With Anything - Semaphore](https://semaphoreci.com/blog/function-calling#:~:text=Function%20calling%20is%20a%20powerful,beyond%20what%20was%20previously%20possible))  effectively executing the steps as given. Because the functions carry out the action, the model’s job is simple and it’s less likely to veer off script. This still uses the API, but if done carefully, we could potentially do it in a single prompt that contains the entire sequence, or a small number of prompts. The advantage is we can harness GPT-4’s reasoning if needed (for error handling or slight adjustments), while mostly just having it rubber-stamp the next action.

**Handling Rate Limits:** If we do involve the LLM for each step (for example, to describe what’s happening or to dynamically verify after each action), we must be mindful of rate limits. GPT-4’s limit of ~3-5 calls per second at best ([GPT-4 rate limits are brutal; use GPT-3.5 instead | Sophia Willows](https://sophiabits.com/blog/gpt-4-rate-limits-are-brutal#:~:text=At%20the%20moment%20the%20limits,token%20limit%20of%20150%2C000%20tokens%2Fmin)) could be problematic if the user tries to execute many short steps rapidly. But in practice, browser actions take a moment (navigations especially), so the pace of steps is naturally throttled by the browser speed. We will also consider using **GPT-3.5** for certain tasks (it has higher rate limits and lower cost) and reserve GPT-4 for more complex reasoning. For instance, the workflow execution can be done by GPT-3.5, and if an error occurs that needs deeper reasoning, escalate to GPT-4. This tiered approach avoids wasting GPT-4 calls on trivial actions.

Additionally, we can implement simple **rate limiters** or batching: if somehow multiple triggers to the LLM are about to happen in quick succession, queue them or combine them. The architecture should queue LLM requests anyway, to avoid conflicts. We can also pre-load some context. For example, before running a workflow, we might call GPT-4 once with a summary: “You will act as an executor of a recorded human task. Here are the steps... If you encounter an issue, you will ask for guidance.” Then, as steps execute, we might not need to call the model at all unless an issue arises (because the actual clicking is done by the tool functions).

**Ensuring Smooth Integration:** We will thoroughly test prompts for instructing the LLM to follow the recorded steps exactly. By using function calling, we reduce the chance of the model producing irrelevant text – it will output a function name and parameters that we defined, which is easy to parse. This **structured approach** makes the model’s behavior predictable and the integration more reliable (no need to parse verbose natural language into an action). It’s essentially treating the LLM as a controller that emits function calls in sequence. OpenAI’s function calling has been shown to keep interactions more deterministic ([Function Calling: Integrate Your GPT Chatbot With Anything - Semaphore](https://semaphoreci.com/blog/function-calling#:~:text=Function%20calling%20is%20a%20powerful,beyond%20what%20was%20previously%20possible))  which aligns with our needs.

For user experience, we also want to avoid long pauses or failures due to model latency or outages. We might implement a fallback: if OpenAI API is not reachable or too slow, the system can notify the user and perhaps allow switching to a local model (since the WebUI supports various LLMs). The plan is to keep the core functionality (recording and basic replay) not *too* dependent on an API – i.e., it should work offline using just the stored script and a local execution engine if needed. The LLM’s added value is in adaptability and understanding, which is secondary for a straightforward replay.

**Avoiding Token Limits:** Another limitation is context length – if the page content is huge and we try to send it to the LLM every step, we could hit token limits. To mitigate this, we won’t generally send full page HTML to the model for each action. Instead, we rely on the recorded selectors. Only in cases where the LLM needs to decide something (e.g., choose one of several similar elements) might we send some page excerpt or ask the model to parse something. We can also use the fact that the WebUI environment might have direct access to the DOM via Playwright – meaning we can programmatically get needed info rather than ask the LLM to infer it from raw text.

In summary, to work within API constraints and ensure a smooth integration, we will: 
- **Minimize calls** by not using the LLM for every trivial action. 
- Use **function calling or structured outputs** to keep interactions predictable and efficient ([Function Calling: Integrate Your GPT Chatbot With Anything - Semaphore](https://semaphoreci.com/blog/function-calling#:~:text=Function%20calling%20is%20a%20powerful,beyond%20what%20was%20previously%20possible)) 
- Possibly use faster/cheaper models for execution steps and reserve powerful ones for complex reasoning or error recovery.
- Implement basic caching or statefulness: if a workflow is run repeatedly, the model could “remember” the plan from the first call (though with function calling this is less of an issue).
- Respect OpenAI’s rate limits by design – our system should function well under those limits by pacing itself (the typical human-speed pace of the agent is far below the 200 req/min limit).

By planning for these limitations *early in the development* (as is advised for anyone building on GPT-4 ([GPT-4 rate limits are brutal; use GPT-3.5 instead | Sophia Willows](https://sophiabits.com/blog/gpt-4-rate-limits-are-brutal#:~:text=Something%20which%20doesn%E2%80%99t%20seem%20to,on%20in%20your%20product%E2%80%99s%20lifecycle)) , we ensure the system will be robust and scalable. If the project grows to where many workflows are run concurrently (hitting rate limits), we can consider scaling horizontally (multiple API keys or using Azure OpenAI with higher limits, etc.), but that’s beyond MVP. For now, a single-user running one task at a time will comfortably stay within limits, and our integration choices will make sure the LLM usage is efficient, keeping the automation responsive and reliable.
